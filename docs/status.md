### Отличия от каркаса Oracelk

Оба файла на сервере правлены руками, рядом лежат `*.scaffold-backup`.

**`nginx.conf` — заменён на сплошной прокси.** Каркас отдаёт `/static/` и
`/media/` сам, из томов. Для нашего сайта это смертельно: 76 МБ обложек лежат
в образе, и платформенный nginx перехватывал бы весь префикс `/media/`, отдавая
из пустого тома — все картинки работ стали бы битыми. Ни сборка, ни локальный
тест этого не ловят, поломка видна только после выката.

**`docker-compose.yml` — убраны тома `media` и `static`.** После замены конфига
они ни на что не ссылались, но продолжали монтироваться в оба сервиса и вводили
бы в заблуждение.

## Образ

Multi-stage: `node:24-alpine` собирает, `nginx:1.27-alpine` отдаёт на **:8000**.

- **99.8 МБ**, из них 79 МБ — медиа отдельным слоем. Правка текста пушит
  килобайты, а не сайт целиком.
- `absolute_redirect off` — обязательно. Контейнер слушает 8000, публичный сайт
  на 443; без этого `/works/syrnik` отвечал бы `301` на `http://…:8000/…`,
  мёртвый за туннелем.
- `try_files $uri $uri/index.html $uri/ =404` — именно в таком порядке, иначе
  индексный модуль редиректит вместо отдачи.
- Кеш из одной `map`: год для хешированных `/_astro/`, сутки для `/media/`,
  ревалидация для html и `/i18n/`, `no-store` для `/admin/`.
- `403` свёрнут в `404`, иначе каталог без индекса запинает в браузере годовой
  immutable-ответ об ошибке.
- `/healthz` для HEALTHCHECK и для возможного http-health модуля Oracelk.

## Выкатка

**Деплоить по sha, никогда по `:latest`.** Oracelk выполняет
`docker compose up -d` без `--pull`, поэтому подвижный тег, уже лежащий на
хосте, не перекачивается: деплой отрапортует успех и молча оставит старый
образ. Оформлено обращением в Oracelk asks 2026-09-03.

Обычный цикл, когда B-24 будет снят:

1. Пуш в `main` → workflow `image.yml` собирает, прогоняет smoke-тест, пушит.
2. Взять тег из сводки запуска (короткий sha).
3. `set_project_image` — проект `elkhovering`, образ `ghcr.io/elkhovering/elkhovering-com:<sha>`.
4. `deploy_project`.
5. При проблемах — `get_project_logs`.

Пока CI не пушит, то же самое руками:

```bash
docker build -t ghcr.io/elkhovering/elkhovering-com:$(git rev-parse --short HEAD) .
gh auth token | docker login ghcr.io -u Elkhovering --password-stdin
docker push ghcr.io/elkhovering/elkhovering-com:$(git rev-parse --short HEAD)
```

### Что проверяет CI перед пушем

Контейнер поднимается и опрашивается — это ловит отказы, которых сборка не
видит: nginx на не том порту, потерянный слой медиа, редирект вместо отдачи на
`/works/syrnik`, `index.html` вместо 404. Если хоть что-то не так, в реестр не
уезжает ничего.
